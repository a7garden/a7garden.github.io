Optimal Route Planner

여러 장소를 돌아야 할 때 가장 빠른 방문 순서를 찾는 문제(TSP)를, 경유지 수에 따라 최적의 알고리즘을 자동 선택하는 하이브리드 최적화로 푼 모바일 웹 앱. O(n!) → 7 HTTP로 줄여 11 지점 기준 99.998% 절감.

1. 앱 화면 — 경로 그래프

출발지·경유지·도착지를 지도 위의 노드로 두고, 최적화된 방문 순서를 엣지(경로선)로 이어 그린다. 아래는 6개 지점을 잇는 최적 경로로, 출발(녹색 ▶)·경유(파란 번호 1–4)·도착(빨강 ■) 마커가 보라색 폴리라인으로 연결된다.

지도 아래 RouteSummary는 각 구간의 예상 소요시간과 이동거리, 그리고 전체 합계를 보여준다. 순서는 드래그 앤 드롭으로 직접 바꿀 수 있고, 바뀌면 즉시 다시 계산한다.

2. 문제 — 왜 어려운가

N개 장소의 최적 방문 순서를 찾는 건 전형적인 외판원 문제(TSP)다. 순열을 전부 시도하는 완전탐색은 O(n!)이고, 각 순열마다 실제 도로 이동시간을 길찾기 API에 물어봐야 하므로 비용이 폭발한다. 

경유지 8개(10 지점) → 순열 8! = 40,320 가지
각 순열마다 Directions API 1회 호출 = 40,320 회 호출

현실에서는 장소가 5–15개 사이인 경우가 대부분이어서, 정확도를 유지하면서 API 호출을 획기적으로 줄이는 것이 이 앱의 핵심 과제였다.

3. 시스템 설계

  • 프론트: Next.js 정적 내보내기(static export) + React 18. 컴포넌트·커스텀 훅 분리 구조.
  • 지도 SDK: Kakao Maps로 지도 렌더링·마커·폴리라인·장소 검색을 처리.
  • 길찾기: Naver Directions API로 실제 도로 기반 이동시간·거리 산출.
  • 백엔드: Firebase Functions에 API 프록시를 두어 클라이언트 키 노출 없이 CORS·키를 처리.
  • 데이터 흐름: 장소 추가 → (경유지 수 분석) → 알고리즘 선택 → 거리 행렬/순열 평가 → 최적 순서로 지도 갱신.

4. 알고리즘 — 실제 동작하는 하이브리드

핵심은 경유지 수에 따라 알고리즘을 자동으로 고르는 하이브리드다. 지금 실제로 동작하는 분기는 세 단계뿐이다. HybridOptimizer.optimize() (src/utils/routeOptimizer.js)는 waypointCount = locations.length - 2로 

if (waypointCount <= 0)         method = 'direct'           // 2 지점
else if (waypointCount <= 8)    method = 'brute_force'      // 1–8 경유
else if (waypointCount <= 10)   method = 'branch_and_bound' // 9–10 경유
// 그 외(11+)는 result = null → "TOO_MANY_LOCATIONS" (전체 12개 상한)
2 지점 직접 계산(direct) · API 1회. 출발→도착 단일 경로.
1–8 경유 완전탐색(brute_force) · 출발·도착 고정, 경유지 모든 순열을 평가. 100% 최적해 보장. 단, 순열마다 실제 API를 호출하므로 호출 수 = (n-2)!.
9–10 경유 Branch and Bound · 1단계에서 모든 지점 쌍의 거리 행렬(O(n²))을 만들고, 2단계에서 BB 가지치기로 순열을 훑는다. 100% 최적해 보장. 최종 경로 1회 검증.

4.1 1–8 경유 — 완전탐색

optimizeBruteForce()는 getPermutations(waypoints)로 모든 순열을 생성하고, 각 순열마다 getOptimalDirections()로 실제 네이버 이동시간을 조회해 최소를 고른다. 호출 수는 (n-2)!이며, 7 지점(5 경유) 기준 120회, 8 지점(6 경유) 기준 720회, 10 지점(8 경유) 기준 40,320회까지 폭발한다. 그래도 n이 작은 구간에서는 Naver API 응답이 빠르고 최적해가 보장된다는 점이 이 구간의 장점이다.

4.2 9–10 경유 — Branch and Bound + 거리 행렬

optimizeBranchAndBound()는 두 단계로 동작한다.

  1. 거리 행렬 구축 — buildDistanceMatrix()로 모든 지점 쌍의 이동시간을 채운다. 대칭이므로 n(n-1)/2회 API 호출로 절반만 채움.
  2. Branch and Bound 가지치기 — BranchAndBoundOptimizer가 행렬 위에서 순열을 나열하며 현재까지의 최솟값을 하한으로 두고 가지치기. 100% 최적해 보장.

순열마다 API를 부르지 않고 행렬 위에서 계산하므로, 호출 수는 n(n-1)/2 + 1로 압축된다. 아래가 그 거리 행렬 — TSP 입력 그래프의 가중치 인접 행렬이다.

4.3 API 호출 절감 — BB 분기 실제 도달 케이스

BB 분기는 11–12 지점(9–10 경유)에서 처음 진입한다. 같은 11 지점(9 경유) 문제를 두 방식으로 풀면 호출 수가 크게 갈린다. 

// 11 지점(9 경유) — BB 분기 진입 최소 케이스
완전탐색 (가정)         : 9! = 362,880 회 HTTP 호출
Branch and Bound (실제) : 11·10/2 + 1 = 56쌍 → batch(10) 묶음으로 6 + 1 = 7 회 HTTP 호출

즉, 9–10 경유 구간에 들어서야 BB가 채택되며 호출 수가 (n-2)! → 7 HTTP로 떨어진다. 1–8 경유 구간은 의도적으로 완전탐색으로 풀어 100% 최적해를 우선시한다.

5. 결과

99.998%
API 호출 절감 (11 지점, BB 진입)
100%
최적해 보장 (≤10 경유)
12
최대 지점 수 (hard cap)

실제로는 두 구간, 모두 최적해 보장. 1–8 경유는 완전탐색으로, 9–10 경유는 Branch and Bound로 풀어 어느 구간이든 100% 최적해를 보장한다. 절감의 의미는 "솔루션 품질"이 아니라 "API 호출 수" — 9–10 경유에서 7 HTTP(11 지점) 또는 8 HTTP(12 지점)로 줄여 응답 지연과 비용을 크게 낮춘다. 11 경유 이상(13 지점 이상)은 의도적으로 거부한다.
